Design audit · 10 September 2026

Dashboard vs iOS design system

Review of index.html against Apple’s Human Interface Guidelines for iPhone: layout margins, the 4-point spacing grid, Dynamic Type (Large / default), and padding conventions used by UIKit / SwiftUI.

Scope is layout, grid, type size, spacing, and padding only. Colour, shaders, copy, and product rules are out of scope except where they change space (full-bleed hero, safe area).

1. Summary 2. iOS reference 3. Layout 4. Grid 5. Typography 6. Spacing & padding 7. Components 8. Token map 9. What to change

1. Summary

The dashboard is already thinking in iOS terms: 16pt page margins, an 8pt spacing scale, SF-style system fonts, dark grouped cards, and safe-area insets. It is closer to Fitness / Health (stacked metric cards) than to a UIKit inset-grouped list. The misses are almost all off-scale type sizes and a few radii that are not on the 4pt grid.

Layout Margins and safe area match iPhone compact. Canvas is locked to 390pt.
Grid / space 8pt rhythm is consistent. 7pt chip radius and 30pt goal-card radius are off-grid.
Type Hierarchy is clear, but sizes sit between HIG styles (36, 26, 18, 16 vs 34, 28/22, 17).
How to read verdicts. Match uses an HIG value (or the 4pt grid). Near is within 1–2pt or a neighbouring text style. Miss is off the type scale, off the 4pt grid, or fights a layout rule (Dynamic Type, 44pt controls). Comparison assumes 1 CSS px = 1 iOS pt on a 1× logical canvas, which is the usual web-to-iPhone mapping. Root font size is the browser default 16px, so 1rem = 16pt.

Type system issues beyond size

Miss No Dynamic Type. Sizes are rem/px locked. -webkit-text-size-adjust: 100% also stops iOS Safari from honouring the user’s text-size setting. HIG: use text styles so type scales.
Near One family for all sizes. Stack is SF Pro Text. Headings ≥ 20pt should use SF Pro Display (automatic on a real iPhone with UIFont.preferredFont; on the web you need both in the stack).
Miss Tracking is handmade. Hero uses −0.035em (~−1.26pt at 36). HIG tracking for Display ~34pt is a small positive or near-zero value in Apple’s table, not a 3.5% squeeze. Section titles use a different tracking than the hero even when they should share a style.
Near All-caps meta. .recovery-data and .section-note are 12pt uppercase + 0.04em. Current iOS grouped-list section headers are Footnote 13pt, sentence/title case, secondary colour. All-caps is a pre–iOS 15 pattern (and watchOS / Fitness sometimes still uses it).

7. Component-by-component

Hero date

Behaves like an emphasized Large Title: bold, tight, first thing under the status bar. Size 36 vs 34, leading 40 vs 41. Treat as Near. Mapping: font: .largeTitle.bold() → 34/41.

Weeks-left bar

Full-bleed stripe with 16pt text inset is an iOS pattern (Health highlights, lock-screen banners). Type 18 Bold is not a style; use Headline 17 Semibold or Title 3 20. Min-height 48 meets 44pt. Near

Goal cards

Two-up metric tiles are Fitness, not Settings. Inner layout is a 2-column grid: 32pt disc + content. Issues that are spatial, not visual taste:

  • Radius 30 is off-grid; --radius-lg is already 28 and used on round cards — two radii for the same elevation.
  • Metric at 36 / line-height 1 in a ~171pt column will wrap or overflow sooner than Title 1 28 would.
  • The 32pt disc is not a 44pt control. Fine if decorative; if it is a chevron/status control, enlarge the hit area without necessarily enlarging the drawing.
  • Support line (“L8yd”) sits 8pt under the metric. Good. It uses body 16 on a 1.12 line-height (18pt), which is denser than Subhead 15/20.

History rows

Each row is a 128pt-tall card. A system inset-grouped cell for this content would be roughly: 16 horizontal inset, ~11–14 continuous corner on the group (not each row if grouped), ~8–12 vertical cell padding, Headline 17 + Subhead 15 + a 28pt capsule. Here every row is an independent 28pt-radius card with 16pt padding and a large min-height, so the list feels airy and “custom app,” not UIKit. Spatially consistent with the goal cards. Near as a custom list.

9. What to change (priority)

  1. Put type on the HIG scale. Replace the custom rem ladder with Large Title 34, Title 1/2 28 or 22, Body 17, Subhead 15, Caption 12. That is the highest-leverage “feels like iOS” change. Nothing else in layout is as visible.
  2. Use real leading, not 1.0 / 1.12 on display sizes. Large Title wants 41pt leading. Metrics with line-height: 1 will collide with the support line and clip.
  3. Snap radii to the 4pt grid. Goal cards 30 → 28 (share --radius-lg). Chips 7 → 8.
  4. Stop blocking text-size adjustment. Remove -webkit-text-size-adjust: 100% if this will be used on iPhone Safari, and prefer px that you treat as pt only at the default size — or switch to a small set of styles that can scale.
  5. Keep the 16 / 8 / 32 space scale. Do not invent 18, 20, or 13 padding. The spacing system is already the iOS one.
  6. Optional tightness. Reduce .round-card min-height so history rows hug content (~72–88 instead of 128) if you want list density closer to UIKit. Keep 128 if you want Fitness-tile density.
  7. Only if this should be a real iPhone app layout: drop the 390pt lock at regular width; use 16pt compact / 20pt regular margins and let cards grow.
